aits shell submit

Run one prompt through an agent CLI and return the answer and session id.

Usage: aits shell submit [flags] (PROMPT | -)

Flags

FlagMeaningDefault
--agent AGENTAGENT CLI to run (required). One of: claude, codex.
--allow-tool TOOLLet the agent run TOOL without asking (claude only), e.g. "Bash(git diff:*)". Repeatable.
--cwd DIRRun the agent in DIR (default: the current directory).
--env NAMEPass the variable NAME from this environment to the agent. Repeatable.
--jsonPrint the result, or the error, as JSON on stdout.
--model MODELRun the agent with MODEL, as its vendor names it (default: the vendor's default).
--reportAsk the agent to end with a typed AITS-REPORT line, returned as report: state done, blocked or failed, summary, question.
--run-dir valueRun the agent in a new directory BASE/ID of its own (ID: the task id), instead of --cwd; see --help.
--session IDContinue the conversation ID: the session_id of an earlier result.
--timeout DURATIONStop the agent after DURATION, e.g. 90s or 30m.30m0s
--worktreeRun the agent in a new detached git worktree of --cwd's repository, under --run-dir or $AITS_HOME/worktree.
--writeLet the agent edit files and run commands in its working directory without asking, inside its vendor's sandbox.

Prompt. PROMPT, or "-" to read it from stdin, at most 16 MiB; more is invalid_input. It may use {{aits.date}} (the run's local date, YYYY-MM-DD), {{aits.task_id}} (the task id; for submit, the run id) and {{aits.run_dir}} (the directory the agent runs in), filled when the run starts, so a queued task gets the day it runs. Another {{aits.NAME}} is invalid_input; any other text, {{ included, is left alone.

A directory per run (--run-dir BASE): when the run starts, aits creates BASE/ID, mode 700, and the agent works there instead of --cwd (the two exclude each other); BASE is created if missing. ID is the task id, or for submit a new id of the same form. The result's dir (a task's run.dir) says where it ran. --worktree makes that directory a detached git worktree of --cwd's repository at its HEAD, under --run-dir BASE or else $AITS_HOME/worktree: one tree per agent, so parallel writers never share one. git must be on PATH; if it fails, nothing runs (a task ends not_started with git's message). aits never removes a worktree: review it, merge it, then git worktree remove it.

Output

With --json, stdout is exactly one JSON object: a result once the agent has
started, otherwise {"error":{"code":"…","message":"…"}}. Without --json,
stdout is the answer for status ok and empty otherwise; everything else
goes to stderr, with control characters in the message, session id and
denied calls shown as Go escapes (\x1b, \r): one "denied: TOOL INPUT"
line per call.

Result fields

status       Always. One of the statuses below.
agent        Always.
session_id   When the agent reported one, on every status; pass it to --session.
answer       For ok, and for incomplete: what the agent wrote before
             its background work was stopped.
exit_code    Always. The agent's exit code; -1 if a signal ended it.
duration_ms  Always.
stderr_tail  Only for agent_failed: the last 4 KiB of the agent's stderr.
message      Every status but ok: one line explaining it.
denied_tools Claude Code only, on every status: the tool of each call
             refused for want of your approval, in order.
             claude -p never stops to ask, and a refusal leaves the
             status as it is: the agent may have finished another way.
denied_calls With denied_tools: one {tool, input} per call, in the same
             order. input is the call's command, file_path,
             notebook_path, path, url or pattern (the first it has), at
             most 500 bytes; none for a call without one. Claude Code
             refuses a loop or a command substitution (for, $(...))
             even when each command in it is allowed; a pipe of
             allowed commands runs. Put such a step in a script.
stopped_tasks
             Only for incomplete, Claude Code only: the description of
             each background agent or workflow that was stopped.
report       With --report, on ok or incomplete: the agent's last line
             "AITS-REPORT {...}" read as {state, summary, question}, where
             state is done, blocked (it needs a decision or information:
             question) or failed. summary and question are cut at 2000
             bytes. The status and the answer are as without it.
report_error With --report, when there is no usable report line: why.
dir          With --run-dir or --worktree: the directory the agent ran in.
usage        What the run spent, when the agent reported it, on any
             status: input_tokens (every prompt token, cached ones
             included), cached_input_tokens, output_tokens and, Claude
             Code only, cost_usd as Claude Code prices it. Claude
             Code's figures cover the whole run, subagents included;
             Codex's add up its turns. aits enforces no budget.

Statuses

ok                The agent answered.
agent_failed      The agent exited non-zero or reported an error.
bad_agent_output  The agent's JSON events were not usable.
output_too_large  One output event exceeded 16 MiB; the agent was stopped.
timeout           --timeout elapsed before the agent exited; it was stopped.
stopped           aits got SIGTERM, SIGINT or SIGHUP before the agent
                  exited, even after a timeout; it was stopped.
incomplete        The agent answered, but background work it was waiting
                  for was stopped before it reported back.

Report (--report). aits appends this to the prompt, after a blank line, and reads the answer's last non-empty line:

When you finish, end your reply with one last line of exactly this form,
with nothing after it:
AITS-REPORT {"state":"done","summary":"one sentence on what you did"}
Use "state":"blocked" with a "question" field when you need a decision or
information to go on, and "state":"failed" when you could not do the task.

Background work. Claude Code runs agents and workflows in the background and gives the agent another turn when each one reports back; the answer is the last turn's. aits sets CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 for claude, so Claude Code waits for that work until --timeout; pass the variable with --env to set your own limit. Background work Claude Code stopped, at that limit or for any other reason, before it reported back makes the run incomplete. A command the agent ran in the background (run_in_background) is not waited for: it is stopped when the agent exits, and the status stays as it is. Codex waits for no background work.

Stopping. on a timeout or a signal, aits sends TERM to the agent's process group and KILL 5s later, or at once on a second signal. It still waits for the group to exit and prints the result.

Model (--model). passed to claude as --model MODEL and to codex as -m MODEL, for a new conversation and a resumed one. aits keeps no list of models: a name the vendor rejects is agent_failed. A name that starts with "-" or has spaces or control characters is invalid_input.

Write (--write). the agent edits files and runs commands without asking, inside its vendor's sandbox; aits opens no network, and your own vendor settings still apply. shell submit (once the agent starts) and task create (once the task is stored) print on stderr, with --json too:

aits: warning: --write lets the agent edit files and run commands in its working directory without asking
claude  --permission-mode acceptEdits and a sandbox in --settings: file
        tools write in the working directory; commands write there and
        in Claude Code's temp directory.
codex   -s workspace-write: commands write in the working directory, /tmp
        and $TMPDIR; .git stays read-only. Without --write codex gets
        -s read-only, a resumed session too.

A write anywhere else fails, such as a build cache under $HOME. A command the sandbox stops is not in denied_tools: it looks like any failed command. Claude Code leaves .claude/.cc-writes in the working directory.

Allowed tools (--allow-tool TOOL): the agent runs TOOL without asking, for this invocation only; every other call that needs approval is still refused and listed in denied_tools. TOOL is Claude Code's own syntax, such as Read, "Bash(git diff:*)" or mcp__server__tool, passed as --allowedTools TOOL; aits does not check that it exists. Without --write an allowed command runs outside any sandbox, with the network; with --write it runs in the sandbox. codex has no list of allowed tools: --allow-tool with codex is invalid_input. A TOOL that is empty, starts with "-", or has a comma or control characters is invalid_input. Like --write it warns on stderr, once per tool:

aits: warning: --allow-tool lets the agent run TOOL without asking

Errors (nothing was started)

unknown_flag        exit 2  No such flag for this command.
invalid_input       exit 2  A flag value, the prompt or an argument is invalid.
agent_not_found     exit 1  The agent CLI is not on PATH.
agent_start_failed  exit 1  The agent CLI could not be started.
stdin_failed        exit 1  The prompt could not be read from stdin.
stopped             exit 1  aits got a signal before the agent started.
internal            exit 1  An unexpected failure inside aits.

Exit codes

0  The status is ok.
1  Any other status, or an error marked exit 1 above.
2  Usage error or invalid input; nothing was started.

aits session search

Find conversations that contain every term, with an id to continue them.

Usage: aits session search [flags] TERM...

Flags

FlagMeaningDefault
--agent AGENTSearch only AGENT's transcripts. One of: claude, codex.
--cwd DIROnly sessions whose working directory is DIR or below it, with or without symlinks resolved.
--jsonPrint the result, or the error, as JSON on stdout.
--limit NReturn at most N results.20
--since DURATIONOnly transcripts changed within DURATION, e.g. 72h.
--source KINDOnly sessions started KIND. One of: interactive, scripted (see Source below).

Output

With --json, stdout is exactly one JSON object:
{"results":[...],"skipped":{"files":N,"lines":N}}, or on failure
{"error":{"code":"…","message":"…"}}. Without --json, each
result is a line "UPDATED_AT  AGENT  SESSION_ID  CWD" and an indented
snippet, and anything skipped is reported on stderr. Text output shows
control characters from transcripts as Go escapes (\x1b, \r); --json
carries the original text. No match is not an error.

Result fields

agent        The agent whose transcript matched.
session_id   Pass it to "aits shell submit --session" to continue.
cwd          The session's working directory, as the agent recorded it.
updated_at   When the transcript file last changed, in UTC; newest first.
snippet      Text around the first term in the newest message with it.

Skipped

files        Transcript paths that could not be read or are not regular files
             (pipes, devices, directories; never opened), and transcripts
             that hold messages but name no session or cwd.
lines        Lines that were not JSON or were longer than 64 MiB. A file that
             --cwd or --source rules out is read no further, so its later
             lines are not counted.

Searched

User and assistant message text, and prompts queued while the agent was
working; every term somewhere in the session, ignoring case. Not tool calls
or their output, model thinking, subagent transcripts (Claude's or Codex's),
compaction summaries, or text the agent CLI adds to a turn by itself
(instructions such as AGENTS.md, reminders, notifications, "!" shell
output, interruption and API-error notices).

Source (--source)

A session's kind is the first value its transcript records:
claude  entrypoint of the first event that has one
          interactive  cli, claude-vscode, claude-desktop
          scripted     sdk-cli (claude -p), sdk-ts, sdk-py
codex   payload.source of the first line (session_meta), when a string
          interactive  cli, vscode
          scripted     exec
A session with no such value, or a value not listed, is of unknown kind:
returned without --source, left out by both values. Observed with Claude
Code 2.1.299 and Codex CLI 0.159.2; not a documented vendor contract.

Transcripts

claude  $CLAUDE_CONFIG_DIR/projects/*/*.jsonl (default ~/.claude)
codex   $CODEX_HOME/sessions/*/*/*/rollout-*.jsonl (default ~/.codex)
Subdirectories that cannot be read are passed over without a count; if a
vendor changes this layout, its sessions are not found. If neither the
variable nor HOME is set for an agent searched, the search fails
(invalid_input).

Exit codes

0  The search ran, with or without results.
1  Stopped by a signal, or an unexpected failure.
2  Usage error or invalid input.

Errors. unknown_flag, invalid_input (exit 2); stopped, internal (exit 1).

aits task

Queue agent runs, work them one at a time, and read their results.

Usage: aits task COMMAND

Commands

CommandWhat it does
createQueue a prompt for an agent; prints the task id.
listList tasks, oldest first.
showShow one task and its run.
waitWait until a task, or all or any of several, is done or failed.
workClaim the oldest claimable task, run it, record the result, exit.
cancelWithdraw a queued task, or stop a running one through its worker.

Run 'aits task COMMAND --help' for details.

Errors. unknown_command, unknown_flag (exit 2).

Running on a schedule. let the OS scheduler start aits, or declare the commands as jobs and run them from aits job sched (see "aits job --help"). A crontab that queues a review each weekday at 09:00 and works the queue every 5 minutes:

0 9 * * 1-5  aits task create --agent claude --cwd ~/src/proj "Review the commits since yesterday for bugs"
*/5 * * * *  aits task work --json >> ~/aits-work.log

work exits 0 with {"status":"empty"} when nothing is claimable, so a run with nothing to do is harmless. Runs that overlap claim different tasks, never the same one, so a slow task can leave several workers running at once; cap them with work --max-running N, which counts running tasks across every worker, or start work from a scheduler that does not overlap a job (launchd does not).

On macOS use a launchd agent in ~/Library/LaunchAgents: ProgramArguments for the command, StartInterval 300 for work or StartCalendarInterval for create, and EnvironmentVariables for what the job needs.

A scheduled job does not get your shell's environment:

PATH   must reach aits and the agent CLI (claude, codex): cron's default
       PATH has neither if they live in ~/.local/bin or Homebrew. Without
       the agent, the task fails with run status not_started.
HOME   must be yours: the agent's login lives there, and the queue too
       unless AITS_HOME is set; create and work must use the same queue.
--env  names variables that work passes to the agent from the worker's
       own environment, so set them in the work job, not the create job.

Claude on macOS keeps its login in the login keychain, which a job started by cron, launchd or SSH cannot read: claude fails with "Not logged in" there even though it works in a terminal. Create a token once with "claude setup-token" (valid a year), keep it in a mode-600 file, and have the work job's script export it before aits task work:

export CLAUDE_CODE_OAUTH_TOKEN="$(cat ~/.config/claude-token)"

aits passes CLAUDE_CODE_OAUTH_TOKEN, like ANTHROPIC_API_KEY, to claude when it is set; never put the token itself in a crontab line or an argument. Do not rely on ~/.claude/.credentials.json, which Claude Code writes when the keychain refuses a write: two copies of one login can sign each other out. A token run has no claude.ai connectors. To keep the keychain login and its connectors, run the jobs from a LaunchAgent instead: declare them in a file and install it with "aits job apply FILE --sched".

A long unattended task may start background agents or workflows (claude): it waits for them until its --timeout, and ends incomplete, not done, if one was stopped before it reported back (see "shell submit --help").

Prompt. PROMPT, or "-" to read it from stdin, at most 16 MiB; more is invalid_input. The prompt, --cwd, --model, --allow-tool and --env names must be valid UTF-8: a task is stored as JSON text.

Output. the task id; with --json {"id":"…","status":"queued"}.

Follow-ups (--after ID). --agent and --cwd, if given, must be ID's (--cwd is made absolute, symlinks not resolved). ID must not have failed or ended without a session, and may have only one follow-up that has not failed (one whose worker died counts until its agent is stopped; try again then). A queued follow-up whose parent does not exist, failed or has no session when done is failed by the next list or work (run status not_started); until then show reports it queued. An unreadable task file fails create (internal).

A follow-up runs with its parent's model unless it gives --model, which applies to the follow-up only. It also takes its parent's --label unless it gives its own.

Labels (--label LABEL). letters, digits, '.', '_' and '-', starting with a letter or digit, at most 100 bytes. A label groups tasks, such as the runs of one scheduled runbook: list --label shows only them, and work --label claims only them.

Continuing a session (--session ID): work runs the task as shell submit --session ID does, in the same conversation, so a failed round or a session found with session search can be continued through the queue. --agent is required; --cwd defaults to the current directory, and should be the session's (the vendor reports a session it cannot find). It has no parent: it is claimable at once, and takes no --model, --write or --allow-tool from anything. --after cannot be combined with it. While another task that is queued or running continues ID (by --session, or as a follow-up of a task done in ID), or one that failed is still having its agent stopped, create refuses it: two agents continuing one conversation at once leave it undefined. aits cannot see an agent it did not start: continue a worker_died round only once no agent of it runs, since its agent may still be running while its worker is gone.

With --write, work runs the task as shell submit --write does, without the warning. A follow-up takes its own --write, never its parent's: without it, the agent resumes without write access. --allow-tool is the same: work grants the tools without warning again, and a follow-up only its own.

        in Claude Code's temp directory.
codex   -s workspace-write: commands write in the working directory, /tmp
        and $TMPDIR; .git stays read-only. Without --write codex gets
        -s read-only, a resumed session too.

A write anywhere else fails, such as a build cache under $HOME. A command the sandbox stops is not in denied_tools: it looks like any failed command. Claude Code leaves .claude/.cc-writes in the working directory.

aits task list

List tasks, oldest first.

Usage: aits task list [flags]

Flags

FlagMeaningDefault
--jsonPrint the result, or the error, as JSON on stdout.
--label LABELShow only tasks labelled LABEL (create --label).
--status STATUSShow only tasks whose status is STATUS: queued, running, done or failed.

The queue is $AITS_HOME/task (default ~/.local/share/aits/task). With neither AITS_HOME nor HOME set, every task command fails (invalid_input).

Output. one line per task, "ID STATUS RUN_STATUS AGENT CREATED_AT" (RUN_STATUS empty for a task with no run); with --json {"tasks":[{"id","status","agent","cwd","created_at","after","session","label","active_at","run"}],"skipped":["ID"]}, with after only for a follow-up, session only for a --session task, label only for a labelled task, active_at only for a running task whose agent has printed output (lease.active_at in show), and run only once a task has one: its status, session_id, started_at, finished_at and message as in show, without the answer (read it with show).

--status STATUS keeps only the tasks with that status (queued, running, done or failed), and --label LABEL only those labelled LABEL; given both, a task must match both. skipped is not filtered. A morning check of a scheduled queue:

aits task list --status failed --json |
  jq -r '.tasks[] | "\(.id) \(.run.status) \(.run.finished_at)"'

Tasks of dead workers are reclaimed first, and queued follow-ups whose parent does not exist, failed or has no session when done are failed (run status not_started). A running task whose lock file is missing cannot be judged: it stays running, with "aits: cannot tell whether the worker of task ID is alive: its lock file is missing" on stderr.

A task file that cannot be read (not a regular file named by a task id, not JSON, not the record of that id, an unknown status, or running without a lease) is skipped and left as it is: its id is in "skipped" (always present, sorted) or, without --json, on stderr as "aits: skipped task ID that could not be read". A running task whose file cannot be read is not reclaimed, and its agent is not stopped; a follow-up of a task whose file cannot be read stays queued.

Exit codes

0  Listed.
1  The queue could not be read or updated.
2  Usage error or invalid input.

Errors. unknown_flag, invalid_input (exit 2); internal (exit 1).

aits task show

Show one task and its run.

Usage: aits task show [flags] ID

Flags

FlagMeaningDefault
--jsonPrint the result, or the error, as JSON on stdout.

The queue is $AITS_HOME/task (default ~/.local/share/aits/task). With neither AITS_HOME nor HOME set, every task command fails (invalid_input).

Task fields (--json)

id           Created by "task create".
status       queued, running, done or failed.
agent, cwd, prompt, timeout_ms, created_at
env          Variable names passed from the worker's environment.
after        For a follow-up: the task whose session it continues.
session      Set by create --session: the session it continues.
model        Set by create --model, or taken from the parent of a
             follow-up: the model the agent runs with.
label        Set by create --label, or taken from the parent of a
             follow-up: groups tasks for list --label and work --label.
write        Set by create --write: the agent runs in its vendor's
             sandbox and may write without asking.
run_dir, worktree
             Set by create --run-dir and --worktree: each run works in
             a directory of its own, run.dir. A follow-up runs in its
             parent's run.dir and takes neither.
report       Set by create --report, or taken from the parent of a

aits job

Usage: aits job COMMAND

Commands

CommandWhat it does

A job is any command aits job run runs once, with a timeout, a lock, a log and alerts. Its schedule is cron's, or job sched's: one aits process that runs the jobs of a file when they are due, under a LaunchAgent that job apply --sched installs (see "aits job sched --help"). A crontab that backs up notes nightly and checks prices every 5 minutes:

MAILTO=""

aits job run

Run a scheduled command once: timeout, lock, log, run record, alerts.

Usage: aits job run [flags] NAME -- COMMAND [ARG...]

Flags

FlagMeaningDefault
--env NAMEPass the variable NAME from this environment to COMMAND and to the alert program. Repeatable.
--jsonPrint the result, or the error, as JSON on stdout.
--on-alert PROGRAMDeliver alerts by running PROGRAM, an absolute path, with the alert as JSON on stdin.
--timeout DURATIONStop COMMAND after DURATION, e.g. 90s or 30m.30m0s

Jobs live in $AITS_HOME/job (default ~/.local/share/aits/job): per job NAME.log (rotated), NAME.json (its state) and NAME.lock. With neither AITS_HOME nor HOME set, every job command fails (invalid_input).

NAME is letters, digits, '.', '_' and '-', starting with a letter or digit, at most 100 bytes. COMMAND is found on PATH and run in aits's working directory, in its own process group, with stdin /dev/null and the explicit environment shell submit gives an agent (PATH, HOME, USER, LOGNAME, LANG, LC_*, TZ, TMPDIR and the proxy variables) plus each --env NAME. aits does not look at what COMMAND is: a job that runs an agent calls shell submit itself.

Log. COMMAND's stdout and stderr are appended to NAME.log between a start line and an end line (time, status, exit code, duration). The log rotates before a run once it reaches 5 MiB; NAME.log.1 to NAME.log.3 are kept.

Overlap. while a run of NAME holds NAME.lock, another run of NAME does not start COMMAND: it is skipped, with one line in the log, and exits 0.

Stopping. on a timeout or a signal (SIGTERM, SIGINT, SIGHUP), aits sends TERM to the group and KILL 5s later, or at once on a second signal. Once COMMAND exits, whatever it left running in its group is killed.

Alerts. aits decides, from NAME.json, whether a run is worth telling; the --on-alert program, if given, delivers it. A failure is any status but ok, skipped and stopped (a stop comes from outside, such as launchctl or a shutdown, and is not the job's failure).

failure     The first failure, or one that differs from the last alerted
            one: another status or exit code, or other output (numbers
            and long hex strings aside).
repeat      The same failure, 15m, 30m, 1h, 2h and 4h after the previous
            alert, then every 6h.
suppressed  The same failure within that time: nothing is delivered.
recovery    The first ok run after a failure; the failure is cleared.
none        Nothing to tell.

The program gets one JSON object on stdin:

{name, kind, status, exit_code, message, finished_at, failing_since,
 failures, unalerted, output_tail, log}

where failures counts the failed runs since failing_since, unalerted the failed runs since the previous alert that were not delivered, output_tail is the last 4 KiB of the run's output, and log is NAME.log. It runs with the same environment as COMMAND, for 30s at most, its output in the log. A program that fails is reported in alert_error and the log; the run's status and exit code stay COMMAND's.

Output. with --json, one run record:

name, status, started_at, finished_at, duration_ms, alert
exit_code    Once COMMAND ran; -1 if a signal ended it.
message      Every status but ok: one line explaining it.
alert_error  When the --on-alert program failed.

Without --json, "NAME STATUS ALERT" on stdout, and the message and the alert error on stderr.

Statuses

ok            COMMAND exited 0.
failed        COMMAND exited non-zero or was killed by a signal.
timeout       --timeout elapsed; COMMAND was stopped.
stopped       aits got a signal; COMMAND was stopped.
start_failed  COMMAND could not be started, or an --env variable is not
              set. It alerts like any failure.
skipped       The previous run still holds the lock; nothing was run.

Exit codes

0  The status is ok or skipped.
1  Any other status, or the job's files could not be written.
2  Usage error or invalid input; nothing was run.

Errors. unknown_flag, invalid_input (exit 2); internal (exit 1).

aits job sched

Run the jobs FILE declares for this host when they are due, until stopped.

Usage: aits job sched [flags] FILE

Flags

FlagMeaningDefault
--jsonPrint the result, or the error, as JSON on stdout.

Jobs live in $AITS_HOME/job (default ~/.local/share/aits/job): per job NAME.log (rotated), NAME.json (its state) and NAME.lock. With neither AITS_HOME nor HOME set, every job command fails (invalid_input).

FILE is job apply's (see "aits job apply --help"). sched runs in the foreground until a signal, and is meant to be started and restarted by a supervisor: job apply --sched installs a LaunchAgent for it on macOS, where a job then has the login keychain, and so claude's claude.ai login and connectors, which cron does not.

A FILE that cannot be reread is reported on stderr and in job list; the jobs read last keep running. Only one sched runs per FILE.

On a signal (SIGTERM, SIGINT, SIGHUP) the running jobs are stopped as job run stops them (status stopped), and sched exits 0 once they have.

0  Stopped by a signal.
1  Another sched holds FILE, or the job directory could not be written.
2  Usage error or invalid input: FILE; nothing was run.
