Principles

15/15 rules, each with its guard

Each principle states the rule, the failure it prevents, and the guard that enforces it. A guard marked review-only cannot be checked mechanically and relies on code review; every other guard is a test or CI check. Guards land with the first code they protect — a guard over code that does not exist yet is not required.

The design rules for aits. Approved in the foundation spec; change them only through an issue. This page renders docs/principles.md.

P1

One binary, command groups with a declared dependency graph

Rule

There is one aits binary. Each command group (model, shell, task, session, and any added later) is one package under internal/<group>. A new group needs its own issue with a use case (P2). The repository may also build aits-gw, a second binary that exists only under P15(4); it may import command groups, and nothing that aits builds may import its packages (internal/gw/...). Allowed dependency edges between groups are declared in one place and form a DAG; lower-level groups (shell, model) never depend on higher-level ones (task). Cross-group calls use the target group's Go API — never exec'ing aits itself, never parsing another group's JSON output.

Prevents

Version skew between separately built tools; resolving the wrong executable from PATH; one JSON shape declared twice and drifting.

Guard

A test scans actual imports and fails on any edge missing from the declared list, or on a cycle. A second test lists the dependencies of ./cmd/aits (go list -deps) and fails if any package under internal/gw appears; it lands with the first internal/gw code.

P2

Build only what has a caller today

Rule

Every feature traces to an issue with a concrete use case: who runs it, with what input, which command, and what result. No reserved states, dead flags, aliases, or config files for a single knob.

Prevents

Declared-but-never-set states, docs naming callers that do not exist, and side products growing inside a core service.

Guard

staticcheck (including unused checks) in CI. Whether a feature has a real caller is review-only.

P3

Stdlib first, no cgo

Rule

Builds use CGO_ENABLED=0. Every direct dependency is listed in docs/dependencies.md with the reason it is needed. Expected early entries: modernc.org/sqlite (pure-Go SQLite with FTS5) and golang.org/x/sys.

Prevents

Dependency sprawl (for example, a telemetry stack pulling in an RPC framework for a CLI) and builds that cannot cross-compile to a static binary.

Guard

CI builds with CGO_ENABLED=0; a check fails when go.mod's direct requirements and docs/dependencies.md disagree.

P4

One grammar

Rule

All commands share one parser. Flags may appear before or after positional arguments; -- ends flag parsing. An unknown command or flag is a usage error (exit 2) — it is never treated as a prompt or silently dropped. No aliases, no implicit default verb. An explicit flag always beats an environment variable. One vocabulary of vendor names across all groups.

Prevents

A typo sent to an agent as a prompt; an environment variable silently overriding --agent; commands disagreeing on flag position and exit codes.

Guard

A table-driven test walks the command tree: every command has help, an unknown flag exits 2, and every command that produces output accepts --json.

P5

Machine-readable by contract

Rule

stdout carries only the result; diagnostics go to stderr. With --json, errors are also printed to stdout as {"error":{"code":"…","message":"…"}} so a caller parses one stream. Exit codes: 0 success, 1 operation failed, 2 usage error or invalid input. A child process's own exit code is reported inside the JSON result, not passed through as aits's exit code. Output shapes are documented in help and docs; before 1.0 they may change.

Prevents

Exit code 1 meaning both "bad usage" and "the agent failed"; results that look successful but are empty.

Guard

Functional tests against the built binary assert stdout/stderr separation and exit codes.

P6

Fail closed, no zero-value success

Rule

Input that cannot be parsed, is outside the allowed set, or conflicts with other input is an error (exit 2). "Cannot determine" is also not allowed through. Every result carries an explicit status value; empty output or a zero value never means success.

Prevents

Flags that some backends silently ignored; zero-value results read as success; arguments parsed wrongly without an error.

Guard

Each feature issue's acceptance includes binary tests for its main failure paths. The CLI refuses to print a result with an empty status, and fails with internal instead; tests check each place that prints one.

P7

One storage root, safe writes

Rule

All project-owned files live under one root, $AITS_HOME (default ~/.local/share/aits), with one subdirectory per command group. One function resolves paths; there are no legacy-path fallbacks. Directories are 0700 and files 0600, tightened on existing paths too. Writes go through temp file plus rename. SQLite schemas are versioned with user_version migrations only. Vendor-owned data (for example ~/.claude) stays where the vendor keeps it.

Prevents

Several namespaces and legacy paths silently shadowing new ones; permission fixes landing one call site at a time; two different migration styles.

Guard

Tests assert actual on-disk permissions. A structural test forbids, outside the storage package, every os function that creates, moves, changes or removes a file or directory, OpenFile and OpenRoot whatever their use (internal/archtest/storage_test.go).

P8

Content and secret hygiene

Rule

A child process receives an explicit environment: its adapter's allowlist plus variables the user names with --env NAME. Prompts are not placed in argv when the vendor accepts stdin. Logs and diagnostics never contain credentials or upstream response bodies. The model gateway's audit record holds metadata only — no prompt or completion content. Captured child output is bounded.

Prevents

Every API key in the parent environment reaching the child; prompts visible in ps; upstream error bodies (which can echo prompt content) written to logs; unbounded output buffered in memory.

Guard

Tests plant a canary secret and assert it is absent from the child environment and argv and from aits's stdout and stderr, on success and on a failure path; a test asserts oversized output is truncated.

P9

Safe defaults for exposure and privilege

Rule

Network listeners bind to 127.0.0.1 by default. A server refuses to start without an auth token, and every endpoint except health requires it. Privilege-raising flags (for example, bypassing a vendor's permission prompts) are per-invocation only — never enabled by environment variable or config — and print a warning on stderr. Only official, documented vendor APIs and CLIs are used; aits never impersonates another client.

Prevents

Listening on all interfaces by default; unauthenticated metrics; terms-of-service risk and constant version-chasing from impersonating subscription clients.

Guard

Binary tests: serve without a token refuses to start; the default bind is loopback; no environment variable enables a privilege-raising flag.

P10

Owned processes, recoverable state

Rule

aits runs in the foreground and never daemonizes itself: it does not fork into the background, detach from its session, re-execute itself or write pid files, and no command starts another aits process. A long-running command, such as a server or a looping worker, is allowed when the user starts it in the foreground and supervises it with a tool of their choice (launchd, systemd, tmux). Every other command works on its own and never requires a running aits process; a long-running process does not own agents that other commands depend on (#111). Each child runs in its own process group; on timeout, cancel or SIGTERM aits sends TERM, waits a bounded grace period, sends KILL, reaps, and still prints a result — with timeout and stop as distinct statuses. Persisted "in progress" state must be recoverable by aits itself (for example, a lock the kernel releases when its holder exits), without manual repair. One user action is one atomic command. These rules apply to aits-gw (P15(4)) as well: it runs in the foreground under a supervisor and never daemonizes itself. Its own commands (aits-gw wait, aits-gw status) may require it to be running; no aits command may. Agents it asks for are queued as tasks and run by aits task work, never as its children, so restarting aits-gw does not stop a running agent.

Prevents

Orphaned agent processes; a task stuck running forever after its worker dies; two-step follow-ups that race a background worker; a stale background server still running after an upgrade; commands that fail because a server is not running; one server crash orphaning every agent.

Guard

Tests with a fake vendor that spawns a grandchild assert nothing survives a timeout or SIGTERM; a test asserts the task of a dead worker is reclaimed, even when its pid now belongs to a live process. A structural test forbids the calls that detach or re-execute aits — os.Executable, os.StartProcess, syscall.ForkExec, syscall.Exec, Setsid, Noctty — outside tests and testdata (internal/archtest/process_test.go). That no command requires a running aits process is review-only.

P11

Clean-room, issue-first

Rule

Every change starts from a self-contained public issue: the problem, the use case, acceptance (exact commands, expected output, main failure cases) and what is explicitly out of scope. The reference implementation informs behaviour and lessons only; code is never copied. Public text never contains the reference's private paths, commit IDs, file names or internal names. An issue lists reference behaviours deliberately not carried over, and why. One pull request per issue, with Closes #n in its description.

Prevents

Importing private code together with its legacy; leaking private information into a public repo.

Guard

Issue and pull request templates; a CI check that the pull request description contains Closes #. "No copied code" and "no private details" are review-only.

P12

Test the built binary, never the user's environment

Rule

Functional tests build aits and run it. Vendors are always fakes: fake claude and codex executables, fake upstream HTTP servers. Every test uses a temporary AITS_HOME and HOME, no external network and no accounts. Tests against real vendors are opt-in behind a build tag and are not part of default CI; they use the real HOME, where vendor credentials live, and keep AITS_HOME temporary. Internal logic and edge-case tables may still use unit tests.

Prevents

Tests that pass only on a developer's machine; tests that read or damage the user's real agent state.

Guard

CI runs the test suite with HOME pointing at a read-only directory, so any test writing to the real environment fails.

P13

Ship together, on supported platforms

Rule

One pull request delivers the code, CLI help, docs, the agent skill (skills/aits/SKILL.md) and tests for a change. The CLI reference is generated from help, never hand-written. Supported platforms are Linux and macOS on amd64 and arm64.

Prevents

Help, docs, the skill agents learn aits from, and behaviour drifting apart.

Guard

TestCLIDocs, run by go test ./... in CI, fails when docs/cli.md differs from the help; TestSkill fails when the skill does not name every command, flag and result status. Whether the skill's prose still matches the behaviour is review-only. The CI matrix covers Linux and macOS.

P14

Small binary, no over-engineering

Rule

The release binary (CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" ./cmd/aits, linux/amd64) stays within the size budget in .github/binary-size-budget; the budget measures aits only, and aits-gw has none unless it gets its own file. A change that would exceed it raises the budget in the same pull request and says which feature needs the bytes and why a smaller way does not work. Heavy standard-library packages (net/http, crypto/*, text/template, regexp and the like) enter only with the feature that needs them, inside that command group. Build the least that meets the issue: no abstraction, option or layer before it has a caller.

Prevents

The binary growing quietly with every import; a heavy package pulled in for one convenience function; general-purpose machinery nobody asked for.

Guard

CI builds the release binary for linux/amd64, prints its size, and fails when it exceeds the budget. Whether code is bigger than its job is review-only.

P15

A toolbox for agents, not a platform

Rule

aits is the tools an agent calls from a shell: it runs other agents (shell), finds earlier conversations (session), coordinates work (task), runs the commands an OS scheduler starts (job), and, once each has a caller, calls models (model) and reaches people and chat platforms as a client of a service that hosts them. A command group is scoped by what aits adds to a run, not by what is run: job does not ask whether its command is an agent (#129). A feature belongs in aits when all of these hold:

  1. its caller is an agent or a script, one command per action, with a --json result (P5, P10);
  2. it runs locally and in the foreground; a long-running command is allowed under P10, and no other command depends on it;
  3. aits adds something of its own: an environment allowlist, sandbox and permissions, timeouts and process groups, recoverable state, one vocabulary across vendors. Passing an API through unchanged does not count;
  4. it fits P3 and P14 for every user of the binary. An integration that needs a 24/7 public endpoint, credentials for many third-party platforms, or dependencies most users never run is hosted elsewhere, and aits is its client. "Elsewhere" may be aits-gw, a second binary in this repository, when all of these hold:
    • aits imports none of its packages (P1 guard), so its dependencies never reach the aits binary and P3 and P14 still hold for every user of aits;
      • P14's budget measures aits only;
      • it is released under its own tag prefix (gw/vX.Y.Z, while aits keeps vX.Y.Z), so a fix for a third-party platform does not force an aits release;
      • its configuration (routes) and credentials live outside the repository, in the user's own files and keychain; the repository holds only generic adapters (P11);
  5. it has a caller today (P2).
Prevents

aits growing into a platform: hosting services that callers depend on; every user shipping integrations only a few run; releases tied to third-party platform fixes. A second binary does not change this: users who never install aits-gw get none of its code, dependencies or releases.

Guard

review-only. An issue for a new command group, or for a change that adds a network dependency, says how it meets each of the five conditions. For aits-gw, the import condition is checked by the P1 guard; the rest stays review-only.

Contributing guide: open an issue first, one pull request per issue, and every review checks the change against these rules.
